# PostHog for Saransh Analytics

Saransh measures its audience with PostHog, not the Google Analytics 4 setup Rajniti uses. Visitors stay anonymous: the only identifier that ever reaches PostHog is a Signup Token, never an email.

**Context**: Saransh is pre-launch. One route exists, and the only thing a Visitor can convert on is the Waitlist Signup. The question with a budget attached is narrow — what fraction of Visitors reach the waitlist form, start filling it, and finish — and the answer changes what the landing page should say. Rajniti answers its own analytics questions with GA4 and a hand-written typed event map, and Saransh inherited a `NEXT_PUBLIC_GA_MEASUREMENT_ID` placeholder from it that was never wired to anything. Copying Rajniti would have been free and would have kept one vendor across both products.

It would also have been the wrong tool. GA4 reports sessions and goal completions; it does not answer "why did this person abandon the form," which is the entire question at this stage. PostHog's funnels and session replay do, and replay in particular collapses weeks of event-taxonomy iteration into an afternoon of watching six recordings. The cost is a second vendor to understand, a second billing relationship, and a sibling product whose analytics no longer looks like this one's.

Two further choices were forced by the first. PostHog needs a stable identifier per person, and the obvious one — the email already collected at signup — would have put personal data into a third-party SaaS on a site with no privacy policy, to answer a question that anonymous counting already answers. And `*.posthog.com` sits on EasyPrivacy, the default blocklist for uBlock Origin and Brave, which would silently drop a large share of an audience that is unusually developer-heavy.

**Decision**: Use PostHog Cloud (US region) for Saransh; leave Rajniti on GA4 and delete the dead GA placeholder from Saransh's environment template. Keep the module in Saransh's frontend rather than Sutra — Sutra ships design tokens and components, and a vendor SDK there would force Rajniti to bundle an analytics library it never calls, the same reasoning that keeps `framer-motion` out of Sutra.

Visitors are anonymous. PostHog's per-browser identifier is the only identity until a Waitlist Signup succeeds, at which point the backend returns a Signup Token — a stored UUID on the waitlist row, distinct from its autoincrementing primary key — and the Visitor is identified by that Token alone. The Token is stable across duplicate signups, so a person who signs up on a phone and then a laptop resolves to one person in PostHog, matching the rule that signing up twice is the same Signup.

Autocapture stays on for the questions nobody thought to ask yet, but the events that define the conversion funnel are declared explicitly in a typed event map and fired by hand. Analytics requests are reverse-proxied through a Next.js rewrite on Saransh's own origin, and a `/privacy` page discloses the analytics, the replay, and the proxy in plain language.

**Consequences**: The funnel survives redesigns — it is defined by typed events rather than DOM selectors, so restyling the landing page cannot silently re-point the metric that decides what the page should say. Visitor counts stop disagreeing with the `waitlist` table for reasons nobody can explain. Nothing in PostHog can be traced back to a person without joining through Saransh's own database, so the blast radius of a PostHog breach is a set of opaque UUIDs.

The proxy deliberately routes around a privacy choice some Visitors made on purpose, which sits uneasily with a product whose premise is accountability. Disclosure on `/privacy` is the mitigation, and it is a weaker one than consent — this is the part of the decision most likely to be revisited. Shipping the Token also widens the waitlist endpoint's contract: it now returns an identifier on both the created and duplicate paths, making the endpoint a stable oracle for whether an email is already on the list, where previously it leaked only a boolean.

Two analytics vendors across two sibling products means a contributor moving between them cannot reuse what they know, and any future shared analytics package must reconcile two different event models. Extraction is deferred until Rajniti has a reason to move; generalising across GA4 and PostHog today would mean designing an abstraction over a disagreement.
