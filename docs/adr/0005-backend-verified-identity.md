# FastAPI Verifies Identity; the Browser Never Holds a Saransh Token

Saransh keeps next-auth for the Google sign-in dance, but FastAPI establishes identity itself: the frontend hands the backend Google's `id_token`, the backend verifies it against Google's JWKS, upserts the User, and mints its own short-lived Saransh JWT. That JWT is stored only on next-auth's server-side `token` object and is never copied onto `session`, so client JavaScript can never read a Saransh credential.

**Context**: The obvious move was to mirror Rajniti, which is the working reference implementation for this feature. Two things make a literal mirror unsafe.

First, Rajniti's API is unguarded. `app/routes/user_routes.py` exposes `PATCH /api/v1/users/<user_id>` taking the id straight from the URL with no token check — next-auth protects the *pages*, not the *API*, so any client with curl can rewrite any profile. That is OWASP A01 broken access control, and copying the shape would copy the hole.

Second, Rajniti's `session` callback runs `session.accessToken = token.accessToken`, which moves the credential out of next-auth's encrypted cookie and into the JSON that `/api/auth/session` returns to anyone who asks. Saransh renders Story titles, summaries, outlet names and image URLs that arrive by Ingest from an Agent rather than from a human reviewer, so its client-side injection surface is wider than Rajniti's, and its frontend dependency tree is a live supply-chain risk like any other.

Sharing the next-auth cookie with the backend was considered and rejected: next-auth v4's session token is a JWE encrypted with A256GCM under a key HKDF-derived from `NEXTAUTH_SECRET`, so FastAPI could not simply decode it — it would have to reimplement next-auth's key derivation and keep chasing it across upstream versions. Backend-owned OAuth via Authlib was also considered, and rejected as a larger deviation than the problem warranted. Supabase Auth shared across both products was rejected because it adds an identity vendor to a system that currently has none, against the independence established in [Separate Database for Saransh](./0003-separate-saransh-database.md).

A first-party httpOnly cookie is viable here and is not usually available to a split Vercel/Cloud Run deployment: `frontend/next.config.mjs` rewrites `/api/v1/*` to the backend unconditionally, so the browser only ever talks to its own origin. We are not taking it, because the token stays server-side regardless and the next-auth cookie already provides the browser-facing session.

**Decision**: next-auth owns the Google redirect only. FastAPI verifies the Google `id_token` against Google's JWKS, upserts the User, and mints a stateless Saransh JWT with a 60-minute expiry, silently re-minted by the `jwt` callback as it nears expiry inside a 30-day next-auth session. A single `get_current_user` dependency guards every authenticated route, and endpoints resolve the acting User from the token's subject, never from a path or body parameter. The Saransh JWT is never assigned to `session`. Client components reach authenticated data through thin Next.js Route Handlers that read the token with `getToken()` and attach it server-side; public Story reads continue to call FastAPI directly through the rewrite. The existing `X-API-Key` ingest guard is unchanged and remains a separate trust path for Agents.

**Consequences**: A stolen Saransh token cannot be revoked — statelessness was chosen over a server-side session table, so there is no sign-out-everywhere and no kill switch, and the 60-minute expiry is the only bound on a compromised token's life. That bargain is only acceptable because the token is unreachable from client JS; if a future change exposes it to the browser, this decision must be revisited and a `sessions` table introduced. Authenticated data cannot be fetched directly from client components, so each authenticated surface needs a Route Handler, which is extra indirection in exchange for one consistent place to shape errors. Server-side rendering of User-specific data must forward the incoming cookie explicitly, which is easy to forget and belongs in a shared helper. Saransh's identity now depends on Google's JWKS endpoint being reachable at sign-in, though not on every request.

**Update, 8 Oct 2026**: The reference above to [Separate Database for Saransh](./0003-separate-saransh-database.md) is out of date. ADR 0003 was superseded by [One Database, Shared Users, Single-Owner Tables](./0006-shared-database-and-users.md): the database is shared with Rajniti, and the User is a row in Rajniti's `users` table. The rejection of Supabase Auth and the rest of this decision stand. Since the 8 Oct 2026 pivot to a national news app, a human reviewer is planned between Ingest and publication; until that exists, the injection-surface argument above still applies as written.
