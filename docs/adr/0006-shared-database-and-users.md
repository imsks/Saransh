# One Database, Shared Users, Single-Owner Tables

Rajniti and Saransh share one production Postgres database. A User is one row in one `users` table, seen by both products. Every table has exactly one owning product whose Alembic history may modify it: Rajniti owns `users`, Saransh owns `stories`, `sources`, `waitlist` and `saransh_user_preferences`. This supersedes [Separate Database for Saransh](./0003-separate-saransh-database.md).

**Context**: ADR-0003 declared that Saransh would get its own database and that neither product would read the other's tables. That never happened. `app/config.py` still defaults `DATABASE_URL` to the `rajniti` database, and `alembic/env.py` sets `version_table = "alembic_version_saransh"` — a custom Alembic version table is only necessary when two migration histories share one database. The documented architecture and the running system disagreed, which is worse than having no ADR, because it invites someone to "fix" the shared database by splitting it.

Building User authentication forced the issue. Rajniti already keys `users.id` on the Google `sub` claim, so both products independently resolve the same human to the same identifier with no coupling at all. But recognition was never the hard part. A username must be globally unique, and across two databases that is not merely difficult but impossible — two people can claim the same handle concurrently and neither insert fails. A single `users` table with a single unique constraint solves for free what separate databases cannot solve at any price. Profile drift disappears for the same reason.

The alternatives were weighed. A shared identity vendor such as Supabase Auth would deliver cross-domain SSO and a shared profile store, at the cost of a new vendor in both products' critical sign-in path and a migration of Rajniti's existing Users. Making Rajniti the identity owner and having Saransh call its API would keep a clean service boundary, but Saransh sign-in would then fail whenever Rajniti is down. Duplicating a Saransh-local user table keyed on `sub` would avoid coupling while reintroducing exactly the username divergence and profile drift we are trying to remove. None justified their cost once the database was already shared in practice.

The cost ADR-0003 correctly identified has not gone away: a bad migration or a runaway query in one product can still harm the other, and neither service's credential is scoped to its own data. We are accepting that, and paying down the sharpest edge of it rather than the whole.

**Decision**: Treat the shared database as the intended architecture rather than as debt, and make table ownership explicit and enforced. Rajniti's Alembic history is the only one that may create or alter `users`; Saransh maps a model over it and writes only genuinely shared profile fields. Saransh owns `saransh_user_preferences`, keyed by `user_id` referencing `users.id`, holding reading language, interest categories, district and Saransh's own onboarding completion flag.

`users.onboarding_completed` means *Rajniti's* onboarding and must never be read as Saransh's — each product tracks its own completion, so a person onboarded into one product is still asked by the other. Saransh's `alembic/env.py` gains an `include_object` filter restricting autogenerate to Saransh-owned tables; without it, `make revision --autogenerate` against production would propose dropping every Rajniti table, and has been safe so far only because local Docker starts an empty database.

**Consequences**: Username uniqueness, shared profile and cross-product recognition all become trivial, and no new vendor enters the sign-in path. In exchange the two products are now permanently coupled at the data layer: a destructive migration in either can take down both, backup and restore is all-or-nothing, and neither credential can be least-privileged without further work. Saransh gains a hard dependency on a table it cannot migrate, so any shared profile field it needs — reading language is the live example — must either be added by a Rajniti migration or live in `saransh_user_preferences` instead. Adding an owned-table filter to autogenerate means new Saransh tables must be registered there deliberately, which is a small recurring tax in exchange for removing a catastrophic footgun.

**Update, 8 Oct 2026**: Confirmed by the founder. Two details changed with the pivot to a national news app. Saransh no longer has a district tier, so `saransh_user_preferences` holds the reader's **state**, not a district, alongside reading language, up to three topics, coming-soon interests and Saransh's onboarding flag. And Saransh's onboarding does not ask for a username; a User may still carry one from Rajniti, and the single unique constraint on `users` remains the reason the table is shared. Saransh will also own a `read_events` table (which Stories a User has seen, per edition), used for the daily limit only and never for ranking.
